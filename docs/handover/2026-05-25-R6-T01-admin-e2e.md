## 1. 결론 (부분 완료 — 배선 완료 + 자격 부재로 AD1 skip 유지)

R5에서 1건 잔여이던 **AD1**(관리자 `is_notice` 토글)을 활성화하기 위한 **인증 storageState 인프라를
`e2e/` 안에 완비**했다. 단, 본 터미널 환경에는 **관리자 자격증명(`E2E_ADMIN_EMAIL`/`E2E_ADMIN_PASSWORD`)과
운영 DB 주입(`E2E_DB_READY=1`)이 없어** AD1은 **설계대로 graceful skip** 상태를 유지한다.
**자격·DB를 주입하면 코드 수정 없이 자동 활성**된다(활성화 절차 §6).

> 핵심 발견: **`app/auth/login` 은 Google OAuth 전용**(이메일/비밀번호 폼 없음)이라 UI 비밀번호
> 로그인이 불가능하다. → storageState는 **UI가 아닌 프로그래밍 로그인**(앱과 동일한 `@supabase/ssr`)으로
> 캡처하도록 구현했다. 관리자 판별은 `isAdminEmail()`(= `smartkdy7@gmail.com`, `lib/supabase/blog.ts`,
> 클라·서버 동일 하드코딩).

## 2. 변경 파일 (5개, 전부 `e2e/` 내부)

| # | 파일 | 변경 |
|---|------|------|
| 1 | `e2e/auth.setup.ts` | **신규** — `setup` 프로젝트. `@supabase/ssr` `signInWithPassword`로 로그인 → 인증 쿠키 캡처 → `e2e/.auth/admin.json`(storageState) 저장 + 성공 마커 `e2e/.auth/admin.ready` 생성. 자격/환경 부재 시 **빈 storageState만 기록하고 graceful 종료**(READY 미생성 → AD1 skip). |
| 2 | `e2e/playwright.config.ts` | projects 3분리: `setup`(`*.setup.ts`) / `chromium`(기존 비인증 29건, `*.setup.ts`·`community-admin-auth.spec.ts` 제외) / `admin`(`community-admin-auth.spec.ts`만, `storageState: e2e/.auth/admin.json`, `dependencies: ['setup']`). |
| 3 | `e2e/community-admin-auth.spec.ts` | **신규** — AD1을 `admin` 프로젝트 전용으로 이관. 활성 조건(`E2E_DB_READY=1` + `admin.ready` + service_role/URL) 충족 시 실행, 아니면 graceful skip. **자체 데이터 생성/정리**(R5 패턴). |
| 4 | `e2e/community-admin.spec.ts` | AD1 제거(상기 파일로 이동). **S-AD1(비로그인 리다이렉트)만 유지** — 비인증 `chromium`에서 그대로 통과. |
| 5 | `e2e/.gitignore` | `.auth/` 추가 — 관리자 쿠키·READY 마커 **커밋 금지**(.env 금지 정신). |

### 설계 결정: 왜 AD1을 새 파일로 분리했나
S-AD1은 **로그아웃** 상태에서 `/admin/board → /auth/login` 리다이렉트를 검증하고, AD1은 **로그인된 관리자**
상태가 전제다. Playwright의 프로젝트별 인증(storageState)은 **파일 단위**로 매칭되므로, 한 파일을 두 인증
상태로 동시에 돌릴 수 없다. → 인증 상태가 정반대인 두 테스트를 파일로 분리(`community-admin.spec.ts`=비인증,
`community-admin-auth.spec.ts`=관리자 인증). 지시서의 "community-admin.spec.ts AD1 해제"는 §4의
"(또는 조건부)" 재량을 사용해 **파일 분리 + 조건부 skip**으로 구현했다.

## 3. auth.setup.ts 메커니즘 (프로그래밍 로그인)

UI 로그인(OAuth)이 불가능하므로, **앱과 동일한 `@supabase/ssr` `createServerClient`**에 인메모리 쿠키 jar
어댑터를 물려 `signInWithPassword`를 호출한다. 이때 `setAll` 콜백으로 들어오는 쿠키가 곧 **미들웨어/서버
클라가 읽는 정확한 포맷**(`sb-<ref>-auth-token`, 청크 포함)이므로, 별도 포맷 가공 없이 그대로
storageState 쿠키로 저장한다(라이브러리 버전 변화에 안전).

- 자격증명 부재 → 빈 `admin.json` + 경고 후 종료(READY 미생성). **setup은 통과**(no-op).
- 자격증명이 **있는데** 로그인 실패 → `expect(...).toBeNull()`로 **표면화(throw)**. `admin`은 `setup` 의존이라
  AD1이 실행되지 않고, 비인증 `chromium` 29건은 영향 없음.
- 세션 쿠키가 storageState 직렬화에서 누락되지 않도록 만료를 미래(7일)로 고정.

## 5. AD1 시나리오 (활성 시 동작)

`admin` 프로젝트(관리자 storageState)에서 실행. R5 신뢰성 패턴대로 **시드에 의존하지 않고 대상을 자체 생성**한다.

1. `beforeAll`: service_role로 `community_posts`에 **익명 일반글**(`free`, `is_notice=false`, 고유 제목
   `E2E 공지대상 <ts>`) 1건 INSERT (author XOR guest CHECK 충족: `guest_nickname`/`guest_password_hash`(bcrypt)/`guest_ip_masked`).
2. `/admin/board` 진입 → 관리자 게이트 통과("📌 공지 게시판 관리") 확인.
3. "최근 글(공지 승격)"의 대상 행 → **공지 등록** 클릭 → `PATCH /api/admin/board` **200** 확정(`waitForResponse`).
4. 재로드 후 "현재 공지"에 대상 노출(**공지 해제** 버튼) 확인.
5. `/board/free`에서 **목록 상단 공지 영역에 대상 제목 노출** 확인.
6. **공지 해제** → `PATCH 200` → "공지 등록" 버튼으로 복귀(일반글) 확인.
7. `afterAll`: 생성 게시글 DELETE(잔여 0).

## 6. 활성화 절차 (운영자 / 다음 세션)

1. **관리자 계정 비밀번호 설정**(필수): `smartkdy7@gmail.com`은 Google OAuth 계정이라 기본적으로 비밀번호가
   없다 → **Supabase Auth 대시보드**에서 해당 사용자에 비밀번호를 설정(또는 service_role
   `auth.admin.updateUserById(id,{ password })`). 앱 로그인 폼은 OAuth 전용이라 **테스트는 비밀번호를 쓰지
   않으면 로그인 불가**.
2. **환경변수 주입**(R5 운영 DB 패턴):
   ```powershell
   $env:E2E_ADMIN_EMAIL    = "smartkdy7@gmail.com"
   $env:E2E_ADMIN_PASSWORD = "<위에서 설정한 비밀번호>"
   $env:E2E_DB_READY       = "1"
   # NEXT_PUBLIC_SUPABASE_URL/ANON_KEY/SUPABASE_SERVICE_ROLE_KEY 를 운영(커뮤니티 적용) 프로젝트로 주입
   ```
3. **AD1 단독 실행**(setup 자동 선행):
   ```powershell
   npx playwright test --config=e2e/playwright.config.ts --project=admin
   ```
4. **전체 회귀**(29 + AD1):
   ```powershell
   npx playwright test --config=e2e/playwright.config.ts   # 기대: 30 passed (29 + AD1)
   ```
5. **쿠키 커밋 방지 확인**: `git status --porcelain e2e/.auth` → 무출력.

### 대안 (비밀번호 설정 없이 — 권고, 미검증)
OAuth 전용 계정에 비밀번호를 두기 싫다면, service_role로 **세션을 발급**하는 방식이 더 현실적이다:
`auth.admin.generateLink({ type:'magiclink', email })`로 받은 `hashed_token`을 anon 클라에서
`verifyOtp({ token_hash, type })`로 교환해 세션을 얻어 쿠키를 캡처. **본 라운드에서 실 검증을 못 해
fallback 코드는 넣지 않았다** — 후속(R6+)에서 운영 DB로 검증 후 `auth.setup.ts`에 분기 추가 권장.
