## 2. 추가된 테이블 스펙 (→ `_SCHEMA_REFERENCE.md` 갱신용 원본)

### 테이블 `user_watchlist`

> 회원 즐겨찾기 동기화 SSOT. 익명은 localStorage, 회원은 이 테이블(기기 간 동기화).
> 개인 소유 데이터 패턴 — `secure_memos`와 동일 RLS 모델.

| 컬럼 | 타입 | NULL | 기본 | 비고 |
|------|------|------|------|------|
| `id` | UUID | - | `gen_random_uuid()` | PK |
| `user_id` | UUID | - | | FK `auth.users(id)` ON DELETE CASCADE |
| `asset_type` | TEXT | - | | CHECK `IN ('CRYPTO','STOCK')` |
| `symbol` | TEXT | - | | CRYPTO=`BTCUSDT` / STOCK=`AAPL` |
| `sort_order` | INTEGER | - | `0` | 목록 정렬 순서 |
| `created_at` | TIMESTAMPTZ | - | `NOW()` | |

**제약**: `UNIQUE (user_id, asset_type, symbol)` — 동일 종목 중복 방지(머지 시 ON CONFLICT DO NOTHING)
**인덱스**: `idx_user_watchlist_user` (`user_id, sort_order`)
**RLS**: 본인(`auth.uid() = user_id`)만 SELECT/INSERT/UPDATE/DELETE (4개 정책, secure_memos 패턴 그대로)
**트리거**: 없음(updated_at 컬럼 미사용 — secure_memos와 달리 수정 빈도 낮고 sort_order만 변동)

> `_SCHEMA_REFERENCE.md` 표(라인 13 근처 `secure_memos` 다음)에 추가:
> `| user_watchlist | 회원 즐겨찾기 동기화 | O | 20260529 |`

## 3. 추가된 엔드포인트 스펙 (→ `_API_REFERENCE.md` 갱신용 원본)

모든 라우트 **회원 전용** — 미회원 `401 {error:"로그인이 필요합니다."}`. 인증은 `lib/supabase/server.ts`의 쿠키 세션(`auth.getUser()`) + RLS 이중 가드. `dynamic = 'force-dynamic'`.

### `GET /api/watchlist`
- 본인 즐겨찾기 목록.
- 200: `{ items: WatchlistItem[], limit: 100 }`
- `WatchlistItem = { assetType: 'CRYPTO'|'STOCK', symbol, sortOrder, createdAt }`

### `POST /api/watchlist`
- body: `{ assetType: 'CRYPTO'|'STOCK', symbol, sortOrder? }`
- 추가(멱등). 이미 존재 시 기존 행 반환.
- 201: `{ item, alreadyExists:false }` (신규) / 200: `{ item, alreadyExists:true }` (기존)
- 400: 입력 오류 / **409: 상한 초과** `{error, limit:100}` (taste #3 회원 100)
- symbol은 서버에서 trim·대문자 정규화, 최대 32자.

### `DELETE /api/watchlist`
- body `{ assetType, symbol }` **또는** 쿼리 `?assetType=&symbol=` 둘 다 허용.
- 삭제(멱등 — 없어도 ok).
- 200: `{ ok:true }` / 400: 입력 오류

### `POST /api/watchlist/sync`
- body: `{ items: [{assetType, symbol, sortOrder?}, ...] }`
- **로컬 우선 병합(taste #2)**: 로컬+DB 합집합 업로드, 중복(UNIQUE)은 DB 기존 유지(로컬 손실 0). 잘못된 항목은 조용히 무시(best-effort).
- **상한(taste #3)**: 합집합 100 초과 시 신규분을 입력 순서로 잘라냄(`skipped` 보고). 단일 호출 입력 상한 500(초과 400).
- 200: `{ items: WatchlistItem[], added, skipped, limit:100 }`
- 로그인 직후 1회 호출 용도(D3 연동).

> `_API_REFERENCE.md`에 위 4개 추가(신규 엔드포인트 섹션).

## 4. SSOT 설계 (`lib/supabase/watchlist.ts`)

- **격리**: crypto/stock/blog 미임포트. `@supabase/supabase-js`의 `SupabaseClient` 타입만 임포트 → SSOT 교차 0 (확인 완료).
- **클라이언트 주입형**: 함수가 `SupabaseClient`(RLS-scoped 서버 클라이언트)를 인자로 받음 → RLS가 본인 행만 보장. `user_id` eq는 방어적 중복 필터.
- export: `MEMBER_WATCHLIST_LIMIT(=100)`, `WatchlistAssetType`, `WatchlistItem`, `WatchlistInput`, `normalizeWatchlistInput`, `fetchUserWatchlist`, `countUserWatchlist`, `addToWatchlist`, `removeFromWatchlist`, `syncWatchlist`, `SyncResult`, `AddResult`.
- 시세 조회는 SSOT 책임 아님 — D3 프론트가 coins/ticker·stock/quote(각 도메인 SSOT)로 별도 조회.

## 6. TODO — D3 연동 계약 (T-A·후속)

D3(회원 동기화)는 T-A의 `useWatchlist` 훅 + 본 API 합류 지점:

1. **로그인 직후 1회**: 로컬(`cm.watchlist.v1`) 목록을 `POST /api/watchlist/sync {items}`로 업로드(로컬 우선 병합). 응답 `items`로 로컬 갱신.
2. **회원이면 DB 소스 전환**: 이후 추가=`POST /api/watchlist`, 삭제=`DELETE /api/watchlist`, 목록=`GET /api/watchlist`.
3. **상한 UX**: POST 409(상한 100) 시 사용자에게 "최대 100개" 안내. sync 응답 `skipped>0`이면 일부 누락 안내.
4. **심볼 표기 일치**: CRYPTO=Binance pair(`BTCUSDT`), STOCK=티커(`AAPL`). 서버가 대문자·trim 정규화하므로 클라이언트도 동일 표기 권장.
5. **localStorage 스키마 1:1**: `{assetType, symbol, sortOrder}` — DB 컬럼과 대응(design-brief §2-3).
