## 1. 작업 요약

v2.0 커뮤니티 피벗(자유/시세/정보 + 코인룸 6종)을 위한 게시판·댓글·추천 CRUD 8개 핸들러를 4개 라우트 파일로 신규 작성. T01 마이그레이션(`community_*` 4테이블)과 T07 미들웨어(`x-client-ip-masked` / `x-client-ip-hash` 헤더) 위에서 동작. 회원/익명 혼용 작성·수정·삭제·추천 토글까지 모두 구현. T15 메인페이지·`/board/[slug]/*` 페이지가 그대로 호출 가능.

## 3. 라우트별 완료 상태

| 라우트 | 상태 | 비고 |
|---|---|---|
| GET /api/board/[slug] | **PASS** | 공지글/일반글 분리, page·limit(max 100)·sort(recent/popular/views/comments)·search(ilike)·category 지원 |
| POST /api/board/[slug] | **PASS** | 회원/익명 분기, bcrypt 해시 저장, IP 마스킹, slug 9종 화이트리스트 |
| GET /api/board/[slug]/[postId] | **PASS** | uuid 검증, view_count 비동기 +1, 첫 100개 댓글 동봉 |
| PATCH /api/board/[slug]/[postId] | **PASS** | 회원=auth.uid 비교 / 익명=bcrypt verify. 허용 필드: title, contentHtml, category, tags, coinSymbol |
| DELETE /api/board/[slug]/[postId] | **PASS** | soft delete (is_deleted=true). guestPassword는 query 또는 body 양쪽 수용 |
| POST /api/community/comment | **PASS** | parent_id로 대댓글 지원, 게시글 존재/삭제 여부 선검증, trigger가 comment_count 자동 증가 |
| DELETE /api/community/comment | **PASS** | soft delete (이미 삭제된 경우도 200 ok 반환 — 멱등) |
| POST /api/community/like | **PASS** | 토글 3분기(없음→INSERT / 같은 value→DELETE / 다른 value→UPDATE), like_count는 트리거가 합산 |

## 4. 권한 검증 로직 위치

### 작성 (POST)
- **`app/api/board/[slug]/route.ts:118` `POST`**: `createClient()` (cookies) → `auth.getUser()`. user 있고 `postAsAnonymous !== true`면 `author_id` 주입, 아니면 익명 (`validateGuestNickname` + `hashGuestPassword` + `x-client-ip-masked`)
- **`app/api/community/comment/route.ts:21` `POST`**: 동일 패턴

### 수정/삭제 (PATCH/DELETE)
- **`app/api/board/[slug]/[postId]/route.ts:80` `verifyEditPermission`**: 단일 헬퍼로 회원/익명 분기
  - 회원 글: `auth.getUser()`.id === row.author_id
  - 익명 글: `verifyGuestPassword(body.guestPassword, row.guest_password_hash)`
  - 반환 status: 401(비번 누락) / 403(불일치) / 404(없음) / 410(이미 삭제)
- **`app/api/community/comment/route.ts:88` `DELETE`**: 인라인 동일 패턴

### 추천 (POST /api/community/like)
- 권한 검증 불필요(누구나 추천 가능). dedup만 보장:
  - 회원: `(post_id, user_id)` UNIQUE 부분 인덱스
  - 익명: `(post_id, ip_hash)` UNIQUE 부분 인덱스 (헤더 `x-client-ip-hash` 필수)

## 5. T15(메인페이지) / 게시판 페이지가 사용할 엔드포인트

### 메인페이지 인기글/공지 위젯
```ts
// 인기 글
fetch(`/api/board/free?sort=popular&limit=5`)
// 통합 HOT (board 무관) — 현재는 board별 호출 후 클라에서 합산해야 함
```

### 게시판 목록 (`/board/[slug]/page.tsx`)
```ts
fetch(`/api/board/${slug}?page=${page}&limit=30&sort=${sortKey}&search=${search}&category=${category}`)
// 응답: { notices, posts, total, page, limit }
// 정렬 키 매핑: latest→recent, popular→popular, comments→comments, views→views
```

### 게시글 상세 (`/board/[slug]/[postId]/page.tsx`)
```ts
fetch(`/api/board/${slug}/${postId}`)
// 응답: { post, comments }
// view_count는 자동 +1 (응답에는 +1 전 값. 한 번 새로고침해야 반영)
```

### 작성/수정/삭제/댓글/추천
| UI 액션 | 호출 |
|---|---|
| 글쓰기 등록 | `POST /api/board/[slug]` body `{ title, contentHtml, category, tags, coinSymbol, postAsAnonymous, guestNickname, guestPassword }` |
| 글 수정 | `PATCH /api/board/[slug]/[postId]` body `{ title?, contentHtml?, ..., guestPassword? }` |
| 글 삭제 | `DELETE /api/board/[slug]/[postId]?guestPassword=` 또는 body |
| 댓글 등록 | `POST /api/community/comment` body `{ postId, parentId?, content, postAsAnonymous, guestNickname?, guestPassword? }` |
| 댓글 삭제 | `DELETE /api/community/comment?commentId=&guestPassword=` |
| 추천/비추 | `POST /api/community/like` body `{ postId, value: 1 \| -1 }` → `{ liked, likeCount }` |

## 6. 미완 / 후속 라운드 후보

본 R1에서 PARTIAL 허용이었던 4·5·6·7·8 라우트도 전부 PASS로 완료. **미완 없음**. 다만 다음은 차후 라운드 권장:

1. **추천 dedup의 회원 전이 케이스**: 같은 IP에서 비로그인 추천 후 로그인하면 user_id 추천이 1번 더 가능 (T01에서 의도된 설계). T13에서 정책 결정 가능.
2. **공지글 생성 라우트**: `is_notice=true` INSERT는 admin만 허용해야 — 현재 POST는 무조건 `is_notice=false`로 강제. 관리자 전용 라우트는 별도 R 라운드에서 (예: `/api/admin/board/notice`).
3. **댓글 like 토글**: 현재는 게시글만. 댓글 추천은 `community_comments.like_count` 컬럼은 있으나 토글 라우트 없음. 차후.
4. **페이지네이션 응답 메타**: `hasMore`, `totalPages` 등은 클라가 `total / limit`으로 계산. 필요 시 응답 가공.
5. **PATCH 후 view_count 차감 / 비번 변경**: 비번 변경 API 없음 — 익명 글은 한 번 작성하면 비번 불변. 필요 시 추가.
6. **추천 응답의 `dislikeCount` 분리**: 현재 `likeCount`는 `SUM(value)` 합산이라 음수 가능. UI에서 추천/비추를 분리해 표시하려면 `SUM(value=1)`·`SUM(value=-1)` 별도 집계 RPC 필요 (T01의 알려진 이슈 §1).

## 8. T15 / 다른 일꾼이 사용할 인터페이스 (요약 4-3 보강)

### Supabase 클라이언트 사용 패턴
- **읽기 (RLS 통과)**: `createClient()` from `lib/supabase/server.ts` — cookies 기반 anon, RLS `is_deleted=false` 정책에 의존
- **쓰기 (RLS 우회)**: `createAdminClient()` from `lib/supabase/admin.ts` — service_role. 익명 글의 UPDATE/DELETE는 RLS에서 차단되므로 service_role 필수 (T01 §"알려진 이슈" §4)
- **세션 조회**: 동일하게 `createClient()` 후 `await supabase.auth.getUser()`. middleware는 `/api/`를 스킵하지만 cookies는 그대로 전달되어 server.ts의 SSR 클라이언트가 인증 토큰 디코딩 가능

### slug 화이트리스트
9종 모두 검증:
```ts
const VALID_SLUGS = new Set([
  "free", "market", "info",
  "coin-btc", "coin-eth", "coin-xrp", "coin-sol", "coin-altcoin", "coin-kimp",
]);
```
- T13 코인룸 라우팅은 이 9종 중 `coin-*` 6종을 직접 사용 가능

### uuid 검증
모든 postId/commentId/parentId 경로·body 파라미터는 `/^[0-9a-f]{8}-[0-9a-f]{4}-...$/i` 정규식으로 사전 검증. SQL 인젝션 방지·400 빠른 응답.
